# NFT Forge — MVP

End-to-end studio for generative NFT collections: AI project blueprint → layer assets → traits, weights and compatibility rules → deterministic generation → batch rendering → gallery review → rarity analytics → QA → export package.

Ships with the flagship validation project, **Space Pirates — Genesis Collection (3,333)**.

## Quick start

```bash
npm install
npm run seed -- --render   # Space Pirates: 49 layer assets, 8 categories, 14 rules, 3,333 tokens rendered + QA
npm run build && npm start # http://localhost:3000
npm test                   # engine + deployment test suites
```

Use `npm run dev` while developing. `npm run seed -- --force` recreates the demo project from scratch.

### AI Architect

When Anthropic credentials are present (`ANTHROPIC_API_KEY`, or a profile from `ant auth login`), blueprints are generated by **Claude Opus 5.5** with structured JSON output. The request also opts into server-side refusal fallbacks (`fallbacks: "default"`). Without credentials, a deterministic offline template provider is used. Providers are pluggable (`src/lib/architect.ts`).

## PRD Definition of Done: verified

Measured on the Space Pirates project:

| Requirement | Result |
|---|---|
| Generate 3,333 unique NFTs | 3,333 tokens in ~160 ms, 3,333 unique DNA |
| Zero invalid trait combinations | 0 (rules enforced during selection, re-verified in QA) |
| Batch rendering + recovery | 3,333 renders in ~73 s (22 ms/token, 4 workers); pause/resume/cancel; resumes from disk |
| 3,333 valid metadata files | 0 invalid (Metaplex and ERC-721 templates) |
| Rarity reports match contents | Recomputed from actual tokens; counts reconcile per category |
| Approved NFTs never change | Approved/locked tokens are byte-identical across reseeds (tested) |
| Deterministic generation | Same seed + config hash → same collection (tested) |
| Export package | 3,333 images + 3,333 JSON + CSV reports + QA report + generation record + SHA-256 manifest (0 mismatches) |

QA's visual-duplicate scan caught a genuine art defect during validation. The Cybernetic Visor fully covers the eyes, so robot tokens that differed only by eye trait rendered identically. A compatibility rule now prevents it.

## Architecture

```
src/lib/engine/   Pure, I/O-free core (unit tested)
  generator.ts    seeded selection, exclude / require / weight rules, uniqueness, locking
  rarity.ts       expected (Monte-Carlo over rules) vs actual, information-content scores, tiers, heatmaps
  metadata.ts     configurable templates: Metaplex, ERC-721
src/lib/          store (atomic JSON + per-project locks), assets (validated ingest, versioning,
                  dedup), render (sharp compositor), jobs (render/export queue), qa, architect
src/app/api/      REST routes
src/app/projects/ UI modules: Overview, AI Architect, Asset Studio, Trait Engine, Generator,
                  Gallery & Review, Rarity, QA, Export, Deployment (roadmap), Settings
scripts/          Space Pirates seed + procedural layer art
```

The PRD recommends Python/FastAPI, Postgres, Redis and S3. This MVP is TypeScript end to end with a local file store, so it runs with only Node installed. The data layout in `data/projects/<id>/` mirrors the PRD's data model, and `src/lib/store.ts` is the single seam for swapping in Postgres and object storage.

### Key design decisions

- **Per-token random streams.** Each token's RNG is keyed by `(seed, tokenId, attempt)`, so changing one rule only changes the tokens that rule touches. After the visor rule was added, 2,745 of 3,333 renders were reused.
- **Renders are content-addressed** (`<tokenId>-<dna>.png`). A render is current exactly when that file exists, so there is no render state to corrupt and interrupted jobs resume for free.
- **Rules apply during selection, not just afterwards.** The engine never proposes invalid combinations. Unsatisfiable configs are reported per token and never silently skipped.
- **Selection order ≠ draw order.** Categories are picked top-to-bottom (rules can depend on earlier picks) and composited by their `layer` value.

## IPFS publishing

`/projects/<id>/publish` produces permanent, content-addressed hosting:
1. All renders are packed into `images.car`. Its root CID becomes the image base `ipfs://<imagesCID>/<id>.png`.
2. Every token's metadata (pointing at those URIs) plus `collection.json` is packed into `metadata.car`. That gives the contract's base URI `ipfs://<metadataCID>/`.
3. The CARs are pinned: automatically to Filebase (set `FILEBASE_ACCESS_KEY`, `FILEBASE_SECRET_KEY`, `FILEBASE_BUCKET`; the root CIDs Filebase reports are checked against ours), or by downloading the CARs and importing them into any CAR-capable pinning service, or with `ipfs dag import images.car metadata.car`.
4. Public gateways confirm availability. Rate-limited answers are reported as inconclusive, not as missing.

CIDs are computed locally (UnixFS, CIDv1, raw leaves, 1 MiB chunks, HAMT-sharded directories), so the final URIs are fixed before anything is uploaded. For Space Pirates the whole pack (573.6 MB of images plus 3,333 metadata files) takes about 10 s.

`node scripts/verify-ipfs-car.mjs [projectId]` cross-checks the packages with an independent implementation (`ipfs-unixfs-exporter`): paths resolve through the sharded directory to bytes identical to the renders, and the hand-computed leaf CIDs are present. The test suite also pins the canonical CID for "hello world".

The Deployment Studio pre-fills these URIs. The Gallery has **Approve all filtered** and **Lock all approved** for finishing review at collection scale.

## Robinhood Chain: primary deployment target

New projects default to **Robinhood Chain** (Arbitrum Orbit L2, chain 4663; testnet 46630; ETH gas), and Space Pirates targets it. `/projects/<id>/deploy` shows the Robinhood Chain studio for these projects.

**Contract:** [`contracts/ForgeCollection.sol`](contracts/ForgeCollection.sol), built on OpenZeppelin 5.6 and compiled in-repo (`npm run compile:contracts`, solc 0.8.38, Cancun):
- Fixed-supply ERC-721 with sequential IDs, minted by the owner in batches (`mintBatch`, `airdrop`).
- `tokenURI = baseURI + id + ".json"`, which matches the export package.
- ERC-2981 royalties, ERC-4906 refresh events and ERC-7572 `contractURI`.
- Permanent `freezeMetadata`.
- A `provenanceHash`: SHA-256 over every image's SHA-256 in token order. The export package ships `provenance.json` so anyone can recompute it.
- No on-chain randomness. Arbitrum's `prevrandao` is constant, and traits are generated off-chain from the seed.

**Validated on the live chain without spending anything:** `npx tsx scripts/robinhood-simulate.ts`. A probe contract deploys the collection, mints 250, and checks token URIs, owners, royalties, interfaces, over-mint and non-owner reverts and freezing, all through `eth_call` on Robinhood Chain Testnet *and* mainnet (all pass). The same run estimates gas:

| | Gas | Cost at current price |
|---|---|---|
| Deploy | ~1.72M | ~0.00003 ETH |
| Mint | ~25.4k per token | — |
| **All 3,333 tokens** | 14 transactions | **≈ 0.0018 ETH on mainnet** |

**Deployment flow:**
1. **Wallet:** the browser wallet is discovered via EIP-6963 (Robinhood Wallet, MetaMask, Rabby, Coinbase…). NFT Forge switches it to Robinhood Chain, or adds the network if it's missing.
2. **Testnet:**
   - deploy with the real provenance hash and royalties
   - mint the first N tokens in batches of 250 (one approval each)
   - publish the source on Blockscout automatically
   - verify independently on-chain: exact bytecode, owner, parameters, provenance, royalties, supply, a sample of owners and token URIs, and that the hosted metadata really is this collection's
   Metadata can come from NFT Forge's preview endpoint or from your own IPFS/Arweave upload.
3. **Mainnet gate** requires all of:
   - ERC-721 metadata
   - full supply, QA passing, all artwork rendered, every token locked
   - a *verified* testnet deployment of the exact same content
   - permanently hosted metadata (ipfs://, ar:// or public https)
   - typing the collection name to approve (single use, bound to the wallet and metadata URI)
4. **Resuming is safe.** Pending transactions are settled first, and minting continues from the on-chain `totalMinted()`, so a run never double-mints.

**Source verification:** automatic on testnet. The mainnet explorer challenges automated clients, so when it refuses, the deployment details offer the exact verification input to download plus a link to verify on Blockscout (or run the `forge verify-contract` command included in the download).

**End-to-end CLI test:** `npx tsx scripts/robinhood-testnet-deploy.ts [projectId] [count]` runs the browser runner with a testnet-only key (gitignored `.robinhood-testnet-key.json`). Fund the printed address at https://faucet.testnet.chain.robinhood.com, which needs a browser because of its bot check, then re-run with `npm start` running.

Set `NEXT_PUBLIC_ROBINHOOD_RPC` to a dedicated provider for mainnet. Robinhood recommends Alchemy, and the public RPC is rate limited.

## Deployment Studio: Solana and Metaplex Core (PRD Phase 5, secondary)

`/projects/<id>/deploy`. Keys never reach the server. The browser wallet signs everything, and the server only records public results (URIs, addresses, signatures), then verifies them on-chain on its own.

1. **Test deployment (devnet):** the first N tokens go through every step:
   - artwork and metadata upload to Arweave via Irys, or bring your own hosted URIs
   - a Core collection with an on-chain Royalties plugin
   - mints into the collection
   - server-side verification: update authority, royalties, URIs, names, owner
2. **Production gate (mainnet):** unlocks only when all of these hold:
   - Solana project on the Metaplex standard
   - full supply generated
   - QA passes and all artwork is rendered
   - every token is locked
   - a *verified* devnet test exists of the exact same content (a fingerprint of config, tokens, metadata template and canvas; review status is excluded, so locking after the test is fine)

   Approval is a separate step: you type the collection name. Each approval is single-use and tied to one wallet.

Mechanics:
- **Upload session key.** Irys signs every file. Rather than prompting the wallet about 6,700 times, a temporary key that lives only in the browser tab is funded once with the estimated upload cost, and unspent SOL is swept back afterwards.
- **Packed, batched mints.** 4 Core mints per transaction, 48 tokens per wallet approval. For 3,333 tokens that's about 834 transactions and about 70 approvals. An optional priority fee helps during congestion.
- **Resumable and reconcilable.** Asset addresses are recorded *before* sending, so an interrupted run is reconciled against the chain on resume.
- **Network diagnostics** on the page check RPC, rent, Irys pricing and transaction building in the browser before you start.

Validation:
- `npx tsx scripts/devnet-simulate.ts` builds the engine's real transactions and simulates them against the live Core program on devnet (no SOL needed): collection, royalties and packed mints all pass.
- `npx tsx scripts/devnet-test-deploy.ts [projectId] [count]` runs the full engine end to end with a devnet-only test key (gitignored `.devnet-test-keypair.json`). The public devnet RPC faucet is closed, so fund the printed address once at https://faucet.solana.com, then re-run.

Set `NEXT_PUBLIC_SOLANA_MAINNET_RPC` (and optionally `NEXT_PUBLIC_SOLANA_DEVNET_RPC`) to a dedicated RPC provider before deploying 3,333 tokens. The public endpoints are rate limited.

## Not built yet

- 3D/Blender pipeline (PRD Phase 4; Blender isn't installed here)
- Public mint (Core Candy Machine); the Studio currently mints the collection to the creator wallet
- Ethereum mainnet, other L2s and Sui adapters (Robinhood Chain and Solana are supported)
- Pinning providers beyond Filebase (CARs work with any CAR-capable service today)
- Auth/RBAC and multi-user
- AI image generation for assets

Background job *history* persists across restarts, and a job that was running shows as "interrupted" and resumes from the files on disk.
